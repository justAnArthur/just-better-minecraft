# 2.16 Frame rate: ≥120 fps at the user's view on a 5K display

**Goal:** the game runs at the display's rate on the user's machine. Today, on an M5 Pro driving a 5K display (5120×2880 physical, 240 Hz), the window maximized at this view shows **41 fps / 24.4 ms** in the HUD:

```
XYZ 57.60 232.67 -4087.75   YAW 257.7  PITCH -18.8   MODE FLY
FACES 2316926  CMDS 3804  cpu-cull  OCCLUDED 0
```

After this task the same view renders at **≥120 fps (≤8.3 ms GPU and CPU)** on the 5K display, never below 60 in flight, and 2560×1440 is measured too. **The look must not regress:** task 2.15's look was just approved, so no visible change, no LOD pop-in, no holes.

- CLAUDE.md;
- the client README (renderer, terrain pass, draw paths, settings, MSAA), the game README (env vars, `far_metrics`);
- docs/tasks/2.15.md (the look this task must keep);
- `crates/client/src/render/{renderer.rs,settings.rs,hiz.rs}`, `render/terrain/{mod.rs,cpu_cull.rs,gpu_cull.rs}`, `render/shaders/{terrain,sky,sky_gradient}.wgsl`, `app.rs`;
- `crates/game/tests/far_metrics.rs` (`look_shots`).

## Scope

### A. A deterministic perf harness (first, committed on its own)

- `far_metrics::perf_views` (ignored): renders offscreen (no vsync) after the world has fully settled, at 2560×1440 and 5120×2880 (`JBM_PERF_RES`), the user's view plus the five `look_shots` sites (`JBM_PERF_VIEWS`).
- Per frame: the CPU time of `Renderer::render` and per-pass GPU time from timestamp queries (`render::timing::GpuTimer`, `Features::TIMESTAMP_QUERY`), faces, commands and draw calls. Prints a table: CPU p50/p95, GPU min/p50/p95, the per-pass p50s.
- Variants (`JBM_PERF_VARIANTS`: `base`, `no_clouds`, `no_water`, `no_sun`, `no_fog`, `flat_fs`, `gpu_cull`, `cpu_cull`) are interleaved frame by frame, so a busy machine's drift hits every variant alike.

### B. Measure, then write the breakdown below — before fixing

### C. Fix it

Candidates: a render-resolution scale for HiDPI (an auto default for very high pixel counts, plus an env and panel override; the HUD stays native); occlusion culling or the GPU-cull path; screen-space-error LOD / fewer faces; shader cost cuts; front-to-back draw order; fewer passes. Pick by measurement.

What this says:

1. **It is pixels, not geometry.** At 640×360 the frame is 1.65 ms whatever the shaders do: that is the vertex/geometry floor of ~1.2–2.1 M faces (6 vertices each, pulled). From 2560×1440 to 5120×2880 (4× the pixels) the frame grows ~3×.
2. **MSAA 4× costs ~10 ms of the 5K frame** (≈15 → 5.3 ms min). On a tile-based GPU most of that is not the multisampling itself but **bandwidth from splitting the scene over passes**: today every frame runs a clear pass, the terrain pass, the sky pass, the debug-lines and outline passes when shown, and an empty resolve pass. Each pass loads and stores the 4× color and the 4× depth — about 236 MB per attachment per load or store at 5K — so the scene moves well over a gigabyte per frame through memory. The sky pass alone (one fullscreen triangle, Equal depth test) costs ~8 ms at 5K for that reason: its shading is cheap, its load and store of two 4× attachments is not.
3. **The terrain fragment shader is ~4 ms at 5K** (`flat_fs`), the fog/haze ~3 ms and the clouds ~1 ms. The terrain shader's `discard` (cutout layers) also turns off Apple's hidden-surface removal for every terrain fragment, so overdraw is shaded in full.
4. **Culling is not the lever here.** cpu-cull draws ~3.5 k commands in 2–3 multi-draws; occlusion would remove little from this open view (the ground hides far terrain only behind ridges), and gpu-cull's Hi-Z build costs ~3 ms at 5K by itself. The CPU (`render()` 1–3.5 ms) is within budget.
5. **Per-pass timestamps overlap on Apple** (a pass's span includes waiting on the previous pass's fragments: the empty resolve pass reads as long as the sky pass), so the per-pass columns are indicative only; the frame span and the ablations are what to trust.

The user's HUD shows 2.3 M faces and 3804 commands where the harness shows 1.2 M and 3494 at the same eye (1.29 M and 3695 at 5120×2560): a wider window widens the horizontal field of view, but not by that much. The rest is likely the in-flight world (cubes still meshing, or not yet replaced by finer levels) where the harness measures a settled one; the frame's cost is in pixels either way.

Plan, in order: (a) one scene pass with the resolve as its store action; (b) a render scale with an auto default for very high pixel counts; (c) cheaper fragments (front-to-back order, an opaque pipeline without `discard`); then re-measure.

## The fix

1. **One scene pass** (`perf(client)`): the terrain, sky, debug lines and outline draw in one render pass. The MSAA resolve is that pass's store action, and the multisampled color and depth are discarded. The clear pass, the separate sky, lines and outline passes, and the empty resolve pass are gone. Each stage splits into `prepare` (culling, buffer writes, gpu-cull's early pass and Hi-Z cull) and `record` (draws inside the pass). On its own this took the user's view at 5120×2880 from 16.5 to about 12.8 ms (min).
2. **A render scale** (`feat(client)`). The scene renders at the depth target's size and a Catmull-Rom composite upscales it; the overlay and egui stay native. The default is auto: native up to 2560×1600 pixels, scaled to that count above, so 5120×2880 renders at 2698×1518 and 5120×2560 at 2862×1431. `JBM_RENDER_SCALE=auto|<0.25..1>` overrides it, and the panel changes it live. This halves the 5K frame again: at the user's view, 9.8 ms native becomes 4.6 ms.
3. **Direction split everywhere** (`perf(client)`). Task 2.13 drew cubes beyond 4 cubes in one command for all six directions. Their back faces, about 35 % of a 2 M-face view, still reached the vertex shader, and vertex work is the frame's floor: 2.6–2.9 ms at 640×360. The default radius is now `u32::MAX`, so every cube draws per direction. Faces drop 31–44 % and commands roughly double (about 3.5 k to 6 k). The CPU pays about 0.2 ms; the GPU saves 0.3–0.7 ms at the spawn and mountain views. Back-face culling dropped the same faces, so the image does not change.
4. A timer fix found on the way (`fix(client)`). Metal caps the counter sample buffers a process can hold, and a query set per ring slot ran out once a dozen renderers were alive (the parallel screenshot tests). The timer now uses one query set.

**Considered and left out:**
- **Indexed drawing** (4 vertices per face instead of 6). It would cut the vertex floor further, but it changes the command layout across the cull shader, both CPU paths and the vertex shader, and the targets are met without it.
- **An opaque pipeline without the cutout `discard`** for coarse levels. Apple's hidden-surface removal would come back for them, but the estimated gain is under 1 ms at the scaled resolution.
- **gpu-cull as the default.** Its Hi-Z build costs more than occlusion saves at these open views; it wins only at spawn_60up.

Against the targets:
- **The user's view at 5K runs at about 6 ms GPU p50 (≈165 fps) and about 1.1 ms CPU**, and its p95 of 6.8 ms is also within 8.3 ms. 5120×2560, the user's maximized window, matches it.
- No look site's p95 exceeds 13.1 ms at 5K auto, so none drops below 60 fps even under load.
- The heaviest sites, spawn_60up and high_300, have a p50 of 9–11 ms on this busy machine. Their min of 7.4–7.7 ms is what an idle GPU should approach.
- At 2560×1440, natively rendered, every view is at or under 6.8 ms p50.
- The `split_4` rows, interleaved frame by frame, are slower at p50 in every row, by 0.03–1.3 ms and typically 0.3–0.6 ms. They draw 45–80 % more faces with 37–47 % fewer commands, and their CPU is 0.15–0.55 ms lower.

**The look.** `look_shots` (1280×720, native, so this tests the scene pass and the split) is **pixel-identical** before and after, for all ten shots, tint included. The render scale applies only above 2560×1600, where the look shots do not reach. There, `JBM_PERF_SHOTS=1` frames at 5120×2880, native and auto, differ by 0.8–1.2 levels mean per channel. Only 0.7–1.7 % of pixels differ by more than 16 levels, all on block edges, and the difference is invisible at the display's 2× point scale. The goldens did not change.
