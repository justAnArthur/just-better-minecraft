# 1.7 Raycast, break and place blocks, re-mesh on change

**Goal:** the player targets a block with the crosshair, breaks it with the left mouse button and places the selected block with the right. The client applies edits optimistically. The server validates each edit, applies it, and broadcasts it to every player who has that cube loaded, within the same tick. A rejected edit is reverted by an authoritative reply. Edited cubes are pinned against eviction, so builds survive walking away, until persistence lands in 2.3.

## Scope

No new dependencies.

### Raycast (`jbm-core`, new `raycast.rs`, pure logic)

- `raycast(origin: DVec3, dir: DVec3, max_dist: f64, mut hit: impl FnMut(BlockPos) -> Option<bool>) -> Option<RayHit>`.
  - Amanatides–Woo voxel DDA.
  - `hit` returns `Some(true)` for a targetable block, `Some(false)` for pass-through and `None` for not loaded. The ray stops at `None` and returns `None`.
- `RayHit { block: BlockPos, face: Face /* or normal: [i8; 3] */, distance: f64 }`.
  - `face` is the face entered.
  - When the origin starts inside a targetable block, the hit is that block, with distance 0 and the face opposite the direction's dominant axis. Document this.
- **Robustness:**
  - Origins exactly on integer coordinates and directions with zero components (no division by zero; use infinities correctly).
  - Negative coordinates, and |x| ≈ 10⁷.
- `REACH = 5.0` blocks, public.
- The targetable predicate is `StateInfo::solid` (via `SolidTable`). Air and water pass through. Comment that per-state outline shapes are later.

### Protocol (`jbm-core`), bump to `PROTOCOL_VERSION = 4`

- `ClientMsg::BreakBlock { pos: BlockPos }`.
- `ClientMsg::PlaceBlock { pos: BlockPos, state: BlockStateId }`. `pos` is the air cell being filled; the client computes it as hit block + face normal.
- `ServerMsg::BlockChange { pos: BlockPos, state: BlockStateId }`, the authoritative state of one block.
- Keep messages plain data. If `BlockPos` or `BlockStateId` lack `Debug, Clone, Copy, PartialEq` for this use, add them.

### Server (`jbm-server`)

**Handling:** edits are handled in phase 1, in message order, as they arrive. They are validated against the player's current authoritative `PlayerState`, as it stands when the message is handled.

**Validation:** reject unless all of these hold.
1. The block's cube is in the server world.
2. The block center lies within `REACH + 1.0` of the player's eye. The margin covers latency.
3. **Break:** the block is not air.
4. **Place:**
   - The target is air.
   - `state` is a registered state and not air.
   - If the state is solid, its unit box does not overlap (strictly) any joined player's box.

**Accepted edit:**
- Set the block in the world cube.
- Insert the cube into a `pinned: HashSet<CubePos>`.
- Queue a `BlockChange` broadcast.

**Rejected edit:** queue a `BlockChange` with the current authoritative state to that player only, if they have the cube in their sent set. This reverts their optimistic edit. Rejections never disconnect.

**Phase 5:** before `Tick`, and before the streaming pass, send queued `BlockChange`s to every player whose sent set contains the cube. This guarantees the "edit shows on the client within one tick" rule.

**Ordering note:** a `CubeData` sent later in the same tick already contains the edit, so it is never stale. Comment why the order holds.

**Eviction:** the eviction step keeps every pinned cube. Replace the 1.5 caveat comment with the rule, and note in the README that pinned cubes grow without bound until 2.3 persistence.

**Generation never overwrites:** inserting a generated cube must not replace an existing world cube (`entry().or_insert`). Add a test that forces the race: request generation, edit or insert the cube, then collect.

**Test reads:** `pinned_count()` and `block(pos) -> Option<BlockStateId>`.

### Client (`jbm-client`)

**`ClientWorld`:**
- `apply(&ServerMsg::BlockChange)` sets the block if the cube is loaded; otherwise it ignores it.
- `set_block(pos, state) -> bool` is used for optimistic edits.
- Both dirty the cube, plus every neighbor cube the block touches through faces, edges or corners. A block at local x == 0 dirties the -X neighbor; one at x == CUBE_SIZE-1 dirties +X; and so on for each combination, up to 7 neighbors. Only loaded neighbors are dirtied.
- A test checks the exact dirtied set for an interior block, a face block, an edge block and a corner block.
- New `WorldChange::Edited(pos)` for the app.

**Edit flow** (new `edit.rs` or inside the app, but keep the logic testable without winit):
- Each frame, raycast from the predicted eye along the camera forward vector, against `ClientWorld`, up to `REACH`. The result is the target, or none.
- **Left button:** if there is a target, break it: optimistic `set_block(air)` and send `BreakBlock`.
- **Right button:** if there is a target, place the hotbar block at `target + face normal`, when that cell is loaded and air and the block would not overlap the predicted player box. Then optimistic `set_block` and send `PlaceBlock`.
- **Hold to repeat:** every 0.25 s while held. The first press acts immediately.
- **Cursor grab:** when the cursor is not grabbed, the first left click grabs it and does nothing else, as it does today.

**Hotbar:** keys 1–9 select among stone, dirt, grass_block, sand, glass, oak_planks, oak_log, leaves and water. Water is placeable but non-solid; it renders through the existing appearance.

**Prediction interplay:** an optimistic edit can change collision for the predicted player. That is fine; server corrections reconcile it.

**Re-mesh:** edits must re-mesh promptly while streaming is busy.
- Edited cubes go to the front of the dirty queue: a separate priority set taken first by `take_dirty`, then nearest-first for the rest.
- The stale-version rule keeps working unchanged.

### Rendering

**Crosshair:** a small centered cross, drawn by the overlay pass with existing overlay machinery or a tiny pipeline. It must be visible on both sky and terrain: use white with a dark outline, or inverted color.

**Target outline:** new `render/outline.rs`.
- A line-list box around the targeted block.
- Expanded by 0.002 to avoid z-fighting.
- Depth-tested.
- Dark, roughly 40% black.
- `Renderer::render` gains an `Option<BlockPos>` for it, and existing callers pass `None`.

**Overlay** shows the target block's position and state name, and the selected hotbar block.

## Tests

**Core raycast unit tests:**
- Axis-aligned hits on each of the six faces, with the correct face and distance.
- A diagonal through a known block sequence. Assert the visited sequence through a recording closure.
- An origin exactly on a grid corner.
- Direction components of zero.
- Negative coordinates, and x ≈ 10⁷.
- `max_dist` is respected, including a hit exactly at `max_dist`.
- A ray stops at `None`.
- An origin inside a solid block.

**Server unit tests:**
- Break and place succeed and broadcast to players with the cube loaded, and only to them.
- **Rejections:** out of reach, unloaded cube, break air, place into a non-air cell, place overlapping a player, place air or an unknown state. Each is answered with the authoritative `BlockChange` to the sender only.
- A pinned cube survives the player walking away (beyond keep) and back. On return, the client receives `CubeData` with the edit.
- `world_cube_count` excludes only unpinned cubes after the player leaves.
- Generation never overwrites an existing cube.

**Testkit integration test `crates/testkit/tests/edit.rs`:**
- **Within one tick:**
  1. Two clients near each other, fully loaded.
  2. Client A sends `PlaceBlock`.
  3. Exactly one `server.step(1)`.
  4. Both A's and B's drains contain the `BlockChange`, before that tick's `Tick` message.
- A third client far away does not receive it.

**End-to-end `crates/game/tests/edit_e2e.rs`,** no GPU:
- `ClientWorld` + `HeadlessServer`.
- Break a surface block next to spawn.
- After one tick, the client world has air there, and `take_dirty` returns the edited cube first.
- The neighbors dirtied match the rule.

**Golden `crates/game/tests/edit_screenshot.rs`** (or extend `terrain_screenshot.rs`), GPU:
- Inline gen, R=3, V=2.
- Break a 3×3, 2-deep pit near spawn, and place a 2-high glass and plank pillar beside it, through the server. All edits go through server messages so the whole path is covered.
- Render from a close camera, about 6 blocks away, with the outline on one block and the crosshair.
- Golden name `edit_spawn`.
- The orchestrator inspects it zoomed. Make sure the pit walls show dirt and stone layers and the AO in the pit corners.
