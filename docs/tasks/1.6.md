# 1.6 Collision, walk and fly, client prediction with server correction

**Goal:** the player is a box that collides with solid blocks. They walk with gravity and jumping, or fly (toggle), still colliding. Movement runs from one shared physics step in `core`. The client predicts it every tick, and the server runs the same step authoritatively. When the server's result differs, the client rewinds to it and replays its unacknowledged inputs. Tests prove nobody falls through floors and that prediction converges.

## Scope

No new dependencies.

### Shared physics (`jbm-core`, new `physics.rs`, pure logic)

**Units:** blocks and seconds, f64.

**Fixed step:** `TICK_DT = 1.0 / 20.0`. Physics always steps one tick at a time; there is no variable dt.

**Constants**, all public and documented in one place (the README lists them):

| constant | value |
|---|---|
| player box | 0.6 × 1.8 × 0.6, feet at the bottom center |
| `EYE_HEIGHT` | 1.62 |
| walk speed | 4.3 |
| sprint speed | 5.6 |
| gravity | 32 (blocks/s²) |
| jump velocity | 9.0 (a jump clears just over 1.25 blocks) |
| terminal fall speed | 78 |
| fly speed | 11 |
| fly sprint speed | 22 |

**Types:**
- `MoveInput { forward: i8, strafe: i8, up: i8 /* -1, 0, 1 */, jump: bool, sprint: bool, yaw: f32 }`. In walk mode `up` is ignored and `jump` jumps. In fly mode `up` moves up/down (Space/Shift) and `jump` is ignored.
- `PlayerState { position: DVec3 /* feet */, velocity: DVec3, on_ground: bool, flying: bool }`, deriving `Debug, Clone, Copy, PartialEq`.
  - `aabb()` returns the box.
  - `eye()` returns position + `EYE_HEIGHT`.
- `trait BlockShapes { fn solid(&self, pos: BlockPos) -> Option<bool>; }`. `None` means the block is not loaded.
  - Collision shape is a full unit box when `StateInfo::solid`, else empty.
  - Per-state collision shapes are a later task. Keep the shape lookup in one function so it can grow.
- `SolidTable`: a `Vec<bool>` indexed by `BlockStateId`, built from a `BlockRegistry`, so the hot path never touches the registry.

**`step(state: PlayerState, input: &MoveInput, world: &impl BlockShapes) -> PlayerState`:**
1. **Wish velocity:**
   - Horizontal: the direction from forward/strafe rotated by yaw, normalized so diagonals are not faster, times speed. Use the same yaw convention as `Camera::forward`: yaw 0 looks toward -Z, positive yaw turns toward +X.
   - Velocity is set directly. There is no acceleration or friction yet, and air control equals ground control.
   - Walk: `velocity.y -= GRAVITY * TICK_DT`, clamped to terminal speed. If `jump && on_ground`, `velocity.y = JUMP_VELOCITY`.
   - Fly: `velocity.y = up * fly speed`. No gravity.
2. **Swept collision**, per axis, in the order Y, then X, then Z:
   - Clip the axis displacement against every solid block box the moving box would cross. Then move.
   - A blocked axis zeroes that velocity component.
   - Touching faces do not overlap. Compute block ranges so that a box resting exactly on `y = 64.0` does not collide with the block below on the X/Z sweeps. Use `floor(min)` to `ceil(max) - 1` for the static axes.
   - Never use an epsilon that lets the box sink into a block. Write a comment explaining the boundary rule.
3. **`on_ground`:** true when the Y sweep was blocked while moving down.
4. **Unloaded blocks:** if any block the swept box touches this tick is not loaded (`None`), the step returns the state unchanged: no movement and no gravity. A player is frozen at the edge of loaded terrain instead of falling into it. Client and server both use this rule, which keeps them in agreement while cubes stream in.
5. **Arithmetic:** only `+ - * /`, `floor`, `ceil`, `min`, `max` and `sqrt` on f64. The one exception is `yaw.sin_cos()`, computed once per step. Comment that this is the only platform-dependent operation, and that server correction absorbs any drift.

**Flying toggle:** an input flag, `fly_toggle: bool` in `MoveInput`, that flips `flying` at the start of the step. The server trusts it for now; Stage 1 is creative-only. Comment that.

### Protocol (`jbm-core`), bump to `PROTOCOL_VERSION = 3`

- `ClientMsg::PlayerInput { seq: u64, input: MoveInput, pitch: f32 }` replaces the placeholder. `seq` starts at 1 and increments by 1 per client tick. Pitch is for display and later use; physics ignores it.
- New `ServerMsg::PlayerState { ack_seq: u64, state: PlayerState }`, the authoritative state after processing input `ack_seq`. It is sent in phase 5 before `Tick`, only in ticks where at least one input was processed.
- `Welcome.spawn` stays. It is the feet position and the initial state, with velocity 0, not on ground, walking.

### Server (`jbm-server`)

**Player:** `Player` holds a `PlayerState` (initialized at spawn), a queue of received inputs and the last processed seq.

**Phase 1** pushes `PlayerInput`s onto the queue. Rules:
- The queue is capped at 20; on overflow, drop the oldest.
- An input whose seq is ≤ the last processed one is ignored.

**Phase 4** (`phase_ecs_systems`), per player in join order:
- Pop up to 4 queued inputs and `step` each one, against a `BlockShapes` view of the server's world. A missing cube means `None` for its blocks.
- Record the last processed seq.
- **Input-driven:** a tick with no queued input does not step the player. Comment that a stalled client freezes in place, and that anti-cheat and timeouts are a later task.

**Phase 5:** send `PlayerState` (before `Tick`) when inputs were processed this tick.

**Streaming center** is now the cube containing the authoritative `PlayerState.position`. Remove `latest_input`'s position use, and update `PlayerView` (expose `state`, `last_seq` and `input_count`).

**Collision lookup cost:** a cube lookup per block is fine. Do not clone cubes.

### Client (`jbm-client`)

**`ClientWorld`** implements `BlockShapes` using a `SolidTable`, which `ClientWorld::new` gains or receives. Keep the constructor simple for tests; for example `ClientWorld::new()` builds the builtin table.

**New `predict.rs`, `Predictor`:** pure logic, no winit.
- Holds the predicted `PlayerState`, the previous state (for render interpolation), the next seq, and a `VecDeque<(u64, MoveInput)>` of unacknowledged inputs.
- `new(spawn: DVec3)`.
- `tick(&mut self, input: MoveInput, world: &impl BlockShapes) -> ClientMsg`:
  1. Steps prediction.
  2. Stores the input.
  3. Returns the `PlayerInput` to send.
  4. Caps pending at 128: past that, drop the oldest and count it.
- `on_server_state(&mut self, ack_seq, state, world)`:
  1. Drops pending inputs with seq ≤ ack.
  2. Re-simulates from the server state through the remaining pending inputs.
  3. If the result differs from the current prediction (exact `PartialEq`), counts a correction and takes the replayed state.
  4. The render interpolation's previous state snaps too: corrections snap, they do not smooth (comment that smoothing is later).
- Accessors: `state()`, `render_position(alpha: f64) -> DVec3` (the eye, interpolated between previous and current), `corrections()`, `pending_len()`.

**Input:** `input.rs` keeps `InputState`.
- Replace `FlyController`'s position update with building a `MoveInput` from held keys and the camera yaw. Mouse look stays per frame.
- Key map: WASD, Space (jump / fly up), Shift (fly down), Ctrl (sprint), and F (toggle fly, one edge per press).

**App:** a fixed 20 Hz sim clock with an accumulator.
- Each sim tick: build the `MoveInput`, call `Predictor::tick` and send the message. This replaces `INPUT_PERIOD` rate limiting.
- At most 5 catch-up ticks per frame; the rest of the accumulator is dropped.
- The camera position is `predictor.render_position(alpha)`.
- `Welcome` creates the predictor at spawn. The sim does not run before `Welcome`.
- `ServerMsg::PlayerState` goes to `on_server_state`.
- Overlay adds:
  - mode (WALK/FLY) and on-ground
  - velocity
  - pending inputs and total corrections

## Tests

**Core physics unit tests:**
- **Falling onto a floor:**
  - A player dropped from 10 blocks above a stone floor comes to rest with feet exactly on the top face (`position.y == floor_top`, bitwise) and `on_ground`.
  - Same from 1000 blocks up: it reaches terminal speed and lands on a single-block-thick floor without tunneling.
- **Walls:**
  - Walking into a wall stops flush (`max.x == wall.x` exactly) and keeps sliding along the free axis.
  - Two-block-high corridor corners: no tunneling through diagonal gaps between blocks that share an edge.
- **Head bump:** jumping under a one-block ceiling clips at the ceiling, and `velocity.y` becomes 0.
- **Jump:** jump height from flat ground is between 1.2 and 1.3 blocks, and the player cannot jump again in mid-air.
- **Fly:**
  - No gravity.
  - Up/down at fly speed.
  - Collides with blocks.
  - The fly toggle flips once per flagged input.
- **Diagonal:** diagonal speed equals straight speed.
- **Unloaded:** a step touching an unloaded block returns the state unchanged.
- **Far from origin:** the same scenarios at x = ±10⁷ give identical relative results.
- **Fuzz:** a seeded random sweep (a small inline LCG, no dependency) of 2000 steps.
  - Random terrain is built from a seeded function.
  - Random inputs.
  - After every step, the player box never overlaps a solid block (strict overlap, touching allowed).

**Client unit tests** (`predict.rs`):
- Server state equal to prediction: no correction, and pending is trimmed.
- Server state off by one block: exactly one correction, and the result equals server state replayed through the pending inputs.
- Replay order is by seq.
- The pending cap holds.

**Server unit tests:**
- Inputs are applied in seq order, and duplicates or old seqs are ignored.
- At most 4 inputs are processed per tick.
- The queue cap drops the oldest.
- `PlayerState` is sent before `Tick` only in ticks with inputs.
- The streaming center follows the authoritative position.

**End-to-end, `crates/game/tests/prediction.rs`:** `HeadlessServer` with inline gen, R=3, V=2, plus `ClientWorld` + `Predictor`, no GPU.
- **Converges:**
  1. Load the world, then run 200 ticks of scripted inputs: walk, jump, turn, sprint, toggle fly, fly up, toggle back and fall.
  2. Each tick, the client sends one input, then `server.step(1)`, then drains.
  3. At the end, after a final drain, the client state equals the last acked server state exactly.
  4. Zero corrections happen after the world finished loading.
- **Latency:** the same script with the server stepping only every second client tick (inputs queue up). It still converges exactly, and corrections stay 0 once loaded.
- **Correction:** remove a block from the client world only (a test hook on `ClientWorld`, `#[cfg(feature = "testing")]`) under the player's path.
  - The client predicts a fall and the server does not.
  - At least one correction occurs.
  - The final state equals the server's.
- **No falling through floors:** the player spawns, falls and lands. After 100 ticks, the server state's feet are at `surface_height(0,0) + 1` exactly, and `on_ground`.

**Existing tests:** update the uses of `PlayerInput`, keeping their meaning. `tests/protocol.rs` and the testkit tests send the new shape.
