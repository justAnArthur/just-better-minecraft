# 2.13 Full detail to ~512 blocks: faster meshing, fewer draws, LOD only far away

**Goal:** LOD0 (full detail) reaches ~512 blocks (16 cubes) around the player on the overworld at the frame budget, and coarse levels start only beyond it. The user's words after the wave D play-test: "use lods for real far away, not near to me". Today LOD0 stops at 256 blocks (`view_radius` 8) and L1 starts right there.

Raising the radius alone multiplies everything by about 4: LOD0 cubes to generate, stream, mesh, upload, cull and draw. This task first measures where that 4× hurts, then cuts the costs that matter, then raises the defaults. Use the 2.12 debug panel and its counters (faces, triangles, draws and cubes per level) for every number.

**Read:**
- CLAUDE.md, the client, server and game READMEs (streaming, surface-following windows, rings, coverage, the face format, meshing rules, draw paths).
- docs/tasks/2.2.md (pages, MDI), 2.6.md (rings), 2.10.md (surface-following windows), 2.12.md (panel, counters, playground).
- `crates/client/src/mesh/*` (`greedy.rs`, `input.rs`, `face.rs`, `seams.rs`, `oracle.rs`, `pool.rs`), `render/terrain/*` (`layout.rs`, `cpu_cull.rs`, `pages.rs`, `stats.rs`, `mod.rs`), `render/shaders/terrain.wgsl`, `terrain_sync.rs`.
- `crates/server/src/server/{config.rs, stream.rs, stream_plan.rs}`, `crates/core/src/lod.rs` (`ring_radii`).

## Scope

Commit in this order. Each step builds and passes the gates on its own.

### A. Baseline measurement (no behavior change)

Add an ignored test or example, `far_metrics` (in `jbm-game`), that runs a real server on the overworld (`DEFAULT_SEED`, game-scale region), settles, and prints a table. Run it at two cameras: spawn, and a mountain spot (find one deterministically, as in 2.10). Run each at `view_radius` 8 and 16, with the rings as today. Measure:
- LOD0 cubes desired, resident, meshed non-empty; cubes resident and drawn per level;
- faces and triangles per level; indirect commands and draw calls;
- mesh time per cube (p50, p99) on the pool, and total time to mesh what settled;
- server settle time (spawn until LOD0 and every ring are ready) and server resident memory (cube bytes);
- client face-page bytes;
- the CPU time of one frame's terrain pass (cull + command build + encode) and the GPU time if timestamp queries are available (otherwise say so).
- **Quad split causes:** re-mesh the settled LOD0 cubes with AO ignored in the merge key, then with the texture layer ignored, and report the quad counts against the real mesher. This shows what AO and layers cost in triangles. Measurement only; the real mesher does not change in this step.

Put the table in the report. The rest of the task is judged against it.

### B. Faster LOD0 meshing (client)

At 16 cubes, flying meshes about 4× as many new cubes per second. `mesh/terrain_like` is ~221 µs today.
- Rewrite the face-visibility pass with bitmasks. A cube is 32 wide, so one `u32` holds one row: for each direction and slice, build the 32×32 visible-face plane with bit operations (opaque/air/non-opaque rules as now, neighbor cubes from the padded input) instead of per-cell tests. Then run the greedy merge over the set bits only, keyed exactly as now (layer, AO, light, octant split at level ≥ 1, skirts, lids).
- **Output must be identical:** the same `PackedFace` list, order included, as the current mesher, on every level. Keep the current sweep as a test oracle (`mesh::oracle`) and assert equality on the existing mesher test corpus, on random cubes (≥ 2,000 seeded cases including mixed opaque, water and glass, and every level ≥ 1 rule), and on real overworld and playground cubes. Goldens therefore stay unchanged.
- **Target:** `mesh/terrain_like` ≤ 100 µs and `mesh/checkerboard` no slower. Report the before and after medians of every mesh bench, measured in the same session.
- If identical output and the bitmask sweep conflict somewhere (merge order, for example), keep identical output and say what that cost.

### C. Fewer draw commands (client)

Today every visible cube issues one indirect command per face direction that can face the camera. That is up to 5 per cube, and on Metal `multi_draw_indirect` is a CPU loop. At 16 cubes, use A's numbers to decide:
- **Per-cube commands beyond a distance:** cubes farther than `direction_split_radius` (setting, default chosen from measurements; start at 4 cubes) draw all their faces in one command. Back faces are then dropped by the rasterizer's back-face culling (already `cull_mode: Back`). Cubes nearer than that keep per-direction commands. Faces are already stored grouped by direction, so a whole-cube command is one contiguous range. Check this in `layout.rs`/`pages.rs`; if they are not contiguous, make them so.
- Same rule on all three paths: cpu-cull MDI, fallback, and gpu-cull (the cull shader writes one command instead of several for far cubes).
- Report commands, draw calls, the terrain pass CPU time and the GPU time before and after, at 8 and 16 cubes. If one command per cube everywhere is no slower on the GPU, say so and pick it (radius 0), with numbers.
- Pixel output must stay identical on all paths: back-face culling and direction skipping drop the same faces. The path-identity and golden tests must pass unchanged.

### D. Server: stream 4× the LOD0 cubes without a hitch

- **Camera window radius:** the LOD0 camera window (`vertical_radius`) applies only within `camera_window_radius` cubes horizontally (new config, default 4). Beyond it, a column streams only its surface span (the 2.10 rule, with its cap and the extra cube below). A digging or flying player still has the full window around them; far columns at the player's depth were invisible anyway (no caves yet). Same idea for the rings if A shows the ring camera windows dominate their cube counts; say which you did.
- Keep the per-tick generation and send budgets, nearest-first order and the keep-set hysteresis. If settle time at 16 cubes is over 2× the time at 8 today (from A), raise the gen budget or the pool size within the tick limit and report the tick time (`server/tick_*`, plus the tick p99 while settling).
- Classic and existing tests: as in 2.10, the desired sets of existing tests must not change in meaning; if any does, explain why.

### E. New defaults: LOD only far away

- `view_radius` default 16 (512 blocks). The panel slider still allows 2..=32.
- **Rings must start beyond LOD0.** Today level *n* reaches `lod_view_radius · 32 · 2^n` blocks, so L1 reaches 512 blocks with `lod_view_radius` 8: exactly the new LOD0 radius, so L1 would draw nothing. Set `lod_view_radius` default 16, so each ring is twice the previous one (512, 1024, 2048, …), and `lod_levels` default 5 (L5 reaches 16 km, the same far reach as today's L6). Fog, fade and the panel follow through `ring_radii` (one rule, unchanged).
- Add a config check: `lod_view_radius ≥ view_radius / 2 + 1`, so L1 reaches past LOD0 by at least one L1 cube. If it is violated (an env override, a slider), clamp with a one-line warning rather than leaving L1 empty. The panel sliders use the same clamp.
- Measure the defaults with A's tool and put the table next to the baseline: cubes, faces, triangles, commands, memory, settle time, terrain pass time.
- **Budget:** at the new defaults on this machine, in the real window (the orchestrator runs it), the autopilot (`JBM_AUTOFLY`) over 2 km has a mean frame time ≤ 16.7 ms and no frame over 50 ms. Headless, the far_metrics terrain pass at 16 cubes is no more than 2× its time at 8 cubes before this task. If the defaults miss the budget after B–D, pick the largest radius that meets it (12 is the next step), keep the ring rule consistent, and report numbers for both.

## Tests

- B: oracle equality (above), and every existing mesher test unchanged.
- C: a unit test that a far cube gets one command covering its whole face range and a near cube gets per-direction commands. The three-path pixel-identity tests pass, and the 60-frame no-popping test passes with the camera crossing `direction_split_radius`.
- D: a stream_plan test that beyond `camera_window_radius` only surface-span cubes are desired, and within it the full window is. A test that a player digging down 100 blocks still gets LOD0 cubes around them.
- E: the ring-radius clamp (config and slider); a render test on the rings scene with tint on: no tinted (non-LOD0) pixel closer than 480 blocks below the horizon at the new defaults (scaled from 2.10's 200-block test).
- `lod_fly` passes at the new defaults (orchestrator runs `--ignored`). The hole tests' tolerances must not grow.
- Goldens unchanged (they use their own configs). If a golden's config takes the defaults and changes, list it and say why.

## Out of scope

- Height-exact LOD and the downsampling rule (2.14).
- Changing what the mesher outputs: AO, T-junction removal, per-block texture lookup in the shader. A's split numbers feed a later decision.
- GPU-cull as the default, Hi-Z changes, face-page compaction.
- Caves, lighting.
