# 1.5 Noise terrain, cube streaming around the player

**Goal:** the server generates terrain and streams cubes to each player, nearest first, within a view radius. It unloads cubes that fall out of range and keeps memory bounded. Generation runs off the tick thread. A headless test proves a client ends up with exactly the right set of cubes, and that the set follows the player as it moves.

## Scope (`jbm-server`, `jbm-testkit`)

No new dependencies. Threads come from `std`.

### Terrain (`terrain.rs`, pure logic)

**Noise:**
- A local 2D gradient (Perlin-style) noise with fractal octaves.
- Deterministic across platforms: use only `+ - * floor` on f64, plus a hash-based gradient pick from a fixed table. No `sin`/`cos`/`exp`, which are not bit-exact across platforms.
- Input is world block coordinates as f64. It must stay well-behaved at |x| ≈ 10⁹: test that it does not produce NaN or extreme values there.
- This noise is temporary. Task 2.1 replaces it with a declarative density graph, so keep it small.

**`Generator`:**
- `Generator::new(seed: u64, blocks: Blocks)` and `generate(&self, pos: CubePos) -> Cube`.
- Output is a pure function of (seed, pos), whatever order cubes are requested in.
- Surface height `h(x, z)` is an integer:
  - base 64
  - large rolling hills of about ±28 from 4–5 octaves
  - a low-frequency term so some areas are flat and others are hilly
- Columns:
  - grass_block at `h`
  - dirt from `h-3` to `h-1`
  - stone below
  - sand instead of grass and dirt where `h ≤ 61`
  - no water, no trees, no caves (later tasks)
- **Fast paths:**
  - A cube whose bottom is above the column-max height of its 32×32 area is `Cube::default()`, with no per-block work.
  - A cube whose top is below `min height - 4` is `Cube::filled(stone)`.
  - Compute the 32×32 heightmap once per (cx, cz) and reuse it across the cy values of that column. A small bounded cache is fine; it must stay bounded.
- Mixed cubes are built with `Cube::from_fn` or bulk index order, never per-block `set` with palette churn.
- `surface_height(x, z) -> i64` is public. The server uses it for spawn: `[0.5, h(0,0) + 2.0, 0.5]`.
- **Tests:**
  - Determinism: generating the same cube twice gives equal cubes (`Cube: PartialEq` compares content).
  - Order independence: generate a 3×3×3 region in two different orders.
  - Different seeds give different terrain.
  - Column layering is correct at a sample column.
  - A cube far above the surface is uniform air, and one far below is uniform stone.
  - No NaN at ±10⁹.
  - Heights stay in the documented range over a 1024×1024 sample.

### Generation pool (`gen_pool.rs`)

- `GenPool::new(threads, Arc<Generator>)`:
  - Named threads `"jbm-gen-N"`.
  - The job queue is a `Mutex<mpsc::Receiver>` or similar. Results come back on an mpsc.
- `request(pos)` and `try_recv() -> Option<(CubePos, Cube)>`.
- Requests are deduplicated while in flight.
- **Shutdown:**
  - Dropping the pool closes the queue and joins every thread. It must never detach and never hang.
  - A worker panic surfaces on the next `try_recv`. It must not vanish.
- **Inline mode:** with `threads == 0` there are no threads. `request` queues, and the server generates on the tick thread up to `gen_budget_per_tick` cubes per tick. This is the deterministic mode tests and benches use.

### Server config and streaming (`server.rs`, `streaming.rs`)

**`ServerConfig`:**

| field | default |
|---|---|
| `seed: u64` | fixed constant |
| `streaming: bool` | true |
| `view_radius: u32` | 8 cubes, horizontal |
| `vertical_radius: u32` | 4 cubes |
| `send_budget_per_tick: usize` | 64, per player |
| `gen_threads: usize` | `available_parallelism() - 2`, min 1 |
| `gen_budget_per_tick: usize` | 64, inline mode only |
| `max_in_flight: usize` | 512 |

**Constructors:**
- `Server::new()` uses the defaults. `Server::with_config(ServerConfig)` takes an explicit one.
- `ServerConfig::protocol_only()` turns streaming off with 0 gen threads. Every existing test and bench that asserts exact message sequences switches to it, so it keeps passing unchanged in meaning. That covers the server.rs unit tests, the run.rs tests where it matters, `server/tick_8_clients` and `tests/protocol.rs`.

**Spawn:** `Welcome.spawn` is the terrain spawn above.

**Desired set** for a player whose center cube is `c` (from their latest `PlayerInput` position, else spawn):
- every cube with `dx² + dz² ≤ R²` and `|dy| ≤ V`
- precompute the offset list once per config, sorted nearest-first (by `dx² + dy² + dz²`, ties broken deterministically)

**Keep set** is the same shape with R+1 and V+1. This hysteresis stops a player standing on a border from making cubes flap.

**Each tick, phase 5, before `Tick` is sent:**
1. Collect finished generation results. In inline mode, generate up to the budget first.
2. Per player, in join order:
   - Send `UnloadCube` for every cube sent to them that is outside their keep set.
   - Walk the desired offsets nearest-first and send `CubeData` for cubes that are generated and not yet sent, up to `send_budget_per_tick`.
   - Request generation for missing cubes, respecting `max_in_flight`.
   - Never send the same cube twice while it stays loaded.
3. **Eviction:** drop generated cubes from server memory when no player's keep set contains them. Edits do not exist yet, so regeneration is exact. Add a comment and a README note that 1.7 must pin edited cubes, or they will be lost, until persistence lands in 2.3.

**Cost:**
- Per-player work per tick must not scan the full desired set when nothing changed.
- Track a "cursor" into the sorted offsets that resets when the center cube changes, or an equivalent scheme.
- The README says what one idle player costs per tick.

**Disconnect:** removing a player frees its sent-set. Its cubes are evicted on the next tick unless another player keeps them.

**Read access for tests:**
- `world_cube_count()`
- `in_flight()`
- `sent_count(PlayerId)`

## Tests

**`crates/testkit/tests/streaming.rs`**, inline generation, `R = 3`, `V = 2`, budget 16:

- **Join:**
  - Connect, then step until the client has received the whole desired set, bounded at 200 ticks.
  - `loaded()` equals the desired set exactly.
  - Every received cube equals `Generator::generate(pos)` for the same seed.
  - The first cube received is the player's own center cube.
- **Move:**
  - Send `PlayerInput` 10 cubes away along +X and step until settled.
  - The client got `UnloadCube` for every cube outside the new keep set, and `loaded()` equals the new desired set.
  - No cube outside the keep set is loaded at the end.
- **Border:** a player oscillating between two adjacent cubes for 20 ticks causes zero unloads (hysteresis).
- **Memory:** after the client disconnects and 2 more ticks pass, `world_cube_count() == 0`.
- **Two players** far apart each get their own set, and neither gets the other's cubes.
- **Threaded:** `gen_threads = 2` gives the same final `loaded()` set and the same cube contents as inline, stepping with a bounded real-time wait (2 s timeout).

**Server unit tests:**
- The streaming offset order is nearest-first.
- The keep-set math.
- `GenPool` shutdown with queued jobs returns promptly.
