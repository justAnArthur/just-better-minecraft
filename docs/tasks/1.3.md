# 1.3 Tick loop, in-process channel, protocol message types

**Goal:** a real server loop and the boundary between client and server. Protocol message enums live in core. A `Link` trait is implemented by an in-process channel pair, and a network socket can implement it later without either side changing. The server runs its tick phases at 20 Hz and talks to connected clients only through links. A headless test drives a client and the server through 100 ticks.

**Read:** CLAUDE.md, READMEs of crates/core, crates/server, crates/testkit. docs/design.md "Architecture overview" and "Simulation".

## Scope

### `jbm-core`, new modules `protocol` and `link`

Task 1.1 is adding `coords`, `block` and `cube` modules to core in parallel. Touch `crates/core/src/lib.rs` only to add your own `pub mod` lines, and touch the core README only by adding a section of your own.

**`protocol`:**

- `pub const PROTOCOL_VERSION: u32 = 1;`
- `PlayerId(pub u32)`.
- `ClientMsg` variants:
  - `Hello { protocol_version: u32, name: String }`
  - `PlayerInput { client_tick: u64, position: [f64; 3], yaw: f32, pitch: f32 }`. This is a placeholder; 1.6 adds real movement input.
  - `Ping { nonce: u64 }`
  - `Disconnect`
- `ServerMsg` variants:
  - `Welcome { player_id: PlayerId, server_tick: u64, tick_rate: u32 }`
  - `Rejected { reason: String }`
  - `Tick { tick: u64 }`, sent to every joined player at the end of each tick
  - `Pong { nonce: u64, server_tick: u64 }`
  - `Disconnected { reason: String }`
- Rules, documented in the module docs:
  - Messages are plain owned data: no `Arc`, no references, no trait objects. They must stay serializable later.
  - Derive `Debug, Clone, PartialEq`.
  - Do not add serde yet.

**`link`:**

- `pub trait Link<Out, In>: Send`:
  - `fn send(&mut self, msg: Out) -> Result<(), LinkClosed>;`
  - `fn try_recv(&mut self) -> Result<Option<In>, LinkClosed>;` never blocks.
  - `LinkClosed` is returned once the other end has been dropped and nothing is left to read. Messages that were already queued are still delivered first.
- Type aliases:
  - `ClientLink = Box<dyn Link<ClientMsg, ServerMsg>>`, the client's end
  - `ServerLink = Box<dyn Link<ServerMsg, ClientMsg>>`, the server's end for one client
- `pub fn in_process_pair() -> (ClientLink, ServerLink)`:
  - Built on `std::sync::mpsc` and unbounded.
  - Both ends must be `Send`, because the server runs on its own thread.
  - Spawn no threads. Core stays free of I/O and threads.
- Unit tests:
  - Order is preserved.
  - `try_recv` on an empty link returns `Ok(None)`.
  - Dropping one end gives `LinkClosed` on the other, after its queued messages drain.
  - The link can be sent across a thread.

### `jbm-server`

**`tick.rs`:**

- Export `pub const TICK_PERIOD: Duration`, the one canonical constant.
- Add `pub fn until_next_tick(&self) -> Duration`, the time left before the next whole tick is due.
- Add unit tests for it.

**`server.rs`: `Server`.**

- `Server::new()` and `add_connection(ServerLink)`.
- A connection is "pending" until a valid `Hello` arrives, then "joined" with a fresh `PlayerId`, starting at 1 and counting up.
- `tick(&mut self)` runs exactly one tick through the design's phases, as private methods called in a fixed order:
  1. **Messages.** Drain every connection's inbound messages, connections in join order and messages in arrival order.
     - `Hello` with the right version → `Welcome`.
     - The wrong version → `Rejected`, then drop the connection.
     - A message other than `Hello` while pending → `Disconnected`, then drop.
     - `Ping` → `Pong`.
     - `PlayerInput` → store it as the player's latest input and count it.
     - `Disconnect` or a closed link → remove the player.
     - Cap messages per connection per tick at 256, so a flooding client cannot stall the tick. Leftovers wait for the next tick.
  2. **Scheduled block ticks.** Empty stub with a doc comment.
  3. **Block update queue.** Empty stub.
  4. **ECS systems.** Empty stub. bevy_ecs comes later; do not add it now.
  5. **Light and outgoing changes.** Send `Tick { tick }` to every joined player.
- `update(&mut self, elapsed: Duration) -> u32`: feed the `TickClock`, run each due tick, and return the count.
- Read access for tests:
  - `tick_count()`
  - `players() -> impl Iterator<Item = PlayerView>`, where `PlayerView` holds id, name, latest input and input count
  - `dropped_ticks()`
- A send to a closed link removes that player. It must never panic.

**`run.rs`: the real-time loop.**

- `pub fn spawn(server: Server) -> ServerHandle`:
  - Starts one named thread, `"jbm-server"`.
  - It loops: measure elapsed time with `Instant`, call `server.update(elapsed)`, then sleep for `until_next_tick()`.
  - New connections arrive through `ServerHandle::connect(&self, ServerLink)`. Use an mpsc of new links that the loop drains at the start of each tick.
- `ServerHandle::stop(self) -> Server` sets a stop flag, joins the thread and gives the `Server` back so tests can inspect it.
- Dropping a `ServerHandle` without calling `stop` also stops and joins the thread. It must never detach.
- If the server thread panics, `stop` must propagate the panic, not swallow it.
- Tests:
  - Start the thread, connect a client, wait until it is welcomed (poll with a 2 s timeout, never an unbounded wait), then stop.
  - Run 300 ms and assert the tick count is between 3 and 12. Keep the bounds loose so a loaded CI machine still passes.
  - Dropping the handle stops the thread.

### Headless integration test (`crates/testkit/tests/protocol.rs`), which is the acceptance test

- **Main test:** connect a client, step 1 tick and expect `Welcome`. Then for 100 ticks, each tick the client:
  - sends `PlayerInput { client_tick: i, position: [i as f64, 64.0, 0.0], .. }` and `Ping { nonce: i }`
  - the server steps 1 tick
  - the client drains and must receive exactly `Pong { nonce: i, .. }` and `Tick { tick }`, with `tick` increasing by 1 every time
- After the loop the server's player has input count 100, and its latest position is `[99.0, 64.0, 0.0]`.
- Two clients get distinct player ids and both receive every `Tick`.
- A wrong protocol version is rejected and the connection is dropped.
- A client that drops its link is removed on the next tick, with no panic.
- A flood of 1000 pings is answered across 4 ticks: 256 per tick, all of them, in order.
